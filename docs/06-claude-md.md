# 06. CLAUDE.md とメモリ

> **この章でわかること**
> - `CLAUDE.md` とは何か、どこに置くのか
> - 何を書き、何を書かないべきか
> - `.claude/rules/` でルールを分割する方法
> - Claude が自分で学習する「オートメモリ」
> - 指示が守られないときのデバッグ手順

---

## 6-1. なぜ必要なのか

**Claude Code のセッションは毎回まっさらな状態から始まります。**
前回「pnpm を使って」と伝えたことは、次のセッションには引き継がれません。

これを解決する仕組みが 2 つあります。

| | CLAUDE.md | オートメモリ |
| --- | --- | --- |
| **書く人** | あなた | Claude |
| **内容** | 指示・ルール | 学んだこと・パターン |
| **範囲** | プロジェクト / ユーザー / 組織 | リポジトリ単位（マシンローカル） |
| **読み込み** | 毎セッション（全文） | 毎セッション（先頭 200 行 or 25KB） |
| **向いている用途** | コーディング規約、作業手順、アーキテクチャ | ビルドコマンド、デバッグの知見、Claude が気づいた好み |

どちらも**「文脈」であって「強制設定」ではありません。** 必ず実行させたい処理は、フック（[08 拡張機能](08-extensions.md#hooks)）を使ってください。

---

## 6-2. まずは `/init`

セッション内で実行するだけです。

```text
/init
```

Claude がコードベースを解析し、ビルドシステム・テストフレームワーク・コードパターンを検出して `CLAUDE.md` の雛形を作ります。
**すでに `CLAUDE.md` がある場合は、上書きせずに改善案を提案します。**

生成された内容をベースに、「Claude が自力では気づけないこと」を書き足していくのが基本的な運用です。

---

## 6-3. どこに置くか

`CLAUDE.md` は複数の場所に置けます。**読み込み順は「広い範囲 → 狭い範囲」** で、後から読まれたものほど近い文脈として扱われます。

| スコープ | 置き場所 | 用途 | 共有範囲 |
| --- | --- | --- | --- |
| **組織ポリシー** | macOS: `/Library/Application Support/ClaudeCode/CLAUDE.md`<br>Linux/WSL: `/etc/claude-code/CLAUDE.md`<br>Windows: `C:\Program Files\ClaudeCode\CLAUDE.md` | 全社の規約、セキュリティポリシー | 組織全員 |
| **ユーザー設定** | `~/.claude/CLAUDE.md` | 個人の好み、全プロジェクト共通 | 自分だけ |
| **プロジェクト** | `./CLAUDE.md` または `./.claude/CLAUDE.md` | チーム共有のルール。**git にコミットする** | チーム全員 |
| **ローカル** | `./CLAUDE.local.md` | 個人のプロジェクト固有メモ。**`.gitignore` に追加** | 自分だけ |

### 階層的に読み込まれる

`foo/bar/` で起動した場合、`foo/CLAUDE.md` と `foo/bar/CLAUDE.md` の両方が読み込まれます（上書きではなく連結）。
モノレポで、ルートと各パッケージにルールを分けたい場合に便利です。

サブディレクトリの `CLAUDE.md` は起動時ではなく、**Claude がそのディレクトリのファイルを読んだタイミングで読み込まれます。**

### 読み込まれたか確認する

```text
/context
```

**Memory files** の欄に自分の `CLAUDE.md` が出ていれば読み込まれています。出ていなければ Claude には見えていません。

## 6-4. 何を書くか

### 基本方針

書式は自由ですが、**短く、人間が読める形で**。

```markdown
# コードスタイル
- ES モジュール（import/export）を使う。CommonJS（require）は使わない
- import は可能な限り分割代入する（例: import { foo } from 'bar'）

# 作業ルール
- 一連のコード変更が終わったら必ず型チェックを実行する
- パフォーマンスのため、テストスイート全体ではなく単体のテストを優先して実行する
```

### 判断基準

各行について **「これを消したら Claude はミスをするか？」** と自問してください。しないなら消します。

| ✅ 書く | ❌ 書かない |
| --- | --- |
| Claude が推測できないシェルコマンド | コードを読めば分かること |
| デフォルトと異なるコードスタイル | 一般的な言語の慣習 |
| テストの実行方法、使うテストランナー | 詳細な API 仕様（リンクで十分） |
| リポジトリの作法（ブランチ命名、PR 規約） | 頻繁に変わる情報 |
| プロジェクト固有のアーキテクチャ判断 | 長い説明やチュートリアル |
| 開発環境の癖（必須の環境変数など） | ファイルごとの説明 |
| 非自明な落とし穴 | 「きれいなコードを書く」など自明なこと |

### いつ追記するか

- Claude が同じ間違いを **2 回** した
- コードレビューで、Claude が知っておくべきだった指摘が出た
- 前のセッションと同じ修正指示をまた打った
- 新しいメンバーにも同じ説明が必要そうだ

### 書き方のコツ

**サイズ**: 1 ファイル 200 行以内を目標に。長いほどコンテキストを食い、遵守率が下がります。

**構造**: Markdown の見出しと箇条書きで整理する。密な段落より読み取りやすくなります。

**具体性**: 検証できるレベルまで具体的に書く。

- ❌ 「コードを適切にフォーマットする」 → ⭕ 「インデントは半角スペース 2 つ」
- ❌ 「変更をテストする」 → ⭕ 「コミット前に `npm test` を実行する」
- ❌ 「ファイルを整理する」 → ⭕ 「API ハンドラは `src/api/handlers/` に置く」

**一貫性**: 矛盾するルールがあると、Claude はどちらかを恣意的に選びます。定期的に見直して、古くなったものや矛盾するものを削除してください。

**強調**: どうしても守らせたいことは `IMPORTANT` や `YOU MUST` を付けると遵守率が上がります。

**git にコミットする**: チームで育てていくファイルです。時間とともに価値が積み上がります。

## 6-5. 他のファイルを取り込む（`@` インポート）

```markdown
プロジェクト概要は @README.md、使える npm コマンドは @package.json を参照。

# 補足の指示
- Git のワークフロー: @docs/git-instructions.md
- 個人用の設定: @~/.claude/my-project-instructions.md
```

- 相対パスは「そのファイルからの相対」で解決されます
- インポートは最大 4 階層までネストできます
- **バックティックで囲めばインポートされません**。`` `@README` `` と書けば単なるテキストです

> **注意**
> インポートしたファイルも起動時にコンテキストへ読み込まれます。**分割は整理のためであって、コンテキスト削減にはなりません。**
> コンテキストを減らしたい場合は、後述の[パススコープルール](#rules-dir)かスキルを使ってください。

> **外部インポートの承認**
> プロジェクトの `CLAUDE.md` が作業ディレクトリの外（例: ホームディレクトリ）のファイルをインポートしている場合、初回に承認ダイアログが出ます。共有プロジェクトに他人がコミットしたファイルから守るための仕組みです。

### `AGENTS.md` を使っている場合

Claude Code が読むのは `CLAUDE.md` であって `AGENTS.md` ではありません。すでに `AGENTS.md` がある場合は、こう書いた `CLAUDE.md` を作ると両立できます。

```markdown
@AGENTS.md

## Claude Code 固有の指示

src/billing/ 配下の変更はプランモードを使うこと。
```

シンボリックリンクでも構いません（Windows は管理者権限が必要なのでインポート推奨）。

```bash
ln -s AGENTS.md CLAUDE.md
```

## 6-6. `.claude/rules/` でルールを分割する

大きめのプロジェクトでは、トピックごとにファイルを分けられます。

```
your-project/
├── .claude/
│   ├── CLAUDE.md           # 全体の指示
│   └── rules/
│       ├── code-style.md   # コードスタイル
│       ├── testing.md      # テスト規約
│       └── security.md     # セキュリティ要件
```

`.md` ファイルは再帰的に検出されるので、`frontend/`・`backend/` のようなサブディレクトリで整理することもできます。

### パススコープルール（コンテキスト節約に効く）

YAML フロントマターの `paths` で、**特定のファイルを扱うときだけ読み込まれるルール**を書けます。

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API 開発ルール

- すべての API エンドポイントで入力バリデーションを行う
- 標準のエラーレスポンス形式を使う
- OpenAPI 用のドキュメントコメントを付ける
```

`paths` が無いルールは常に読み込まれます。パターンの例:

| パターン | マッチするもの |
| --- | --- |
| `**/*.ts` | すべての TypeScript ファイル |
| `src/**/*` | `src/` 配下すべて |
| `*.md` | プロジェクトルートの Markdown |
| `src/**/*.{ts,tsx}` | 複数拡張子（ブレース展開） |

### ユーザーレベルのルール

`~/.claude/rules/` に置いたルールは、そのマシンの全プロジェクトに適用されます。プロジェクトのルールのほうが優先されます。

### 複数プロジェクトで共有する

シンボリックリンクが使えます。

```bash
ln -s ~/shared-claude-rules .claude/rules/shared
ln -s ~/company-standards/security.md .claude/rules/security.md
```

## 6-7. オートメモリ（Claude が自分で覚える）

あなたが何も書かなくても、Claude が作業しながら学んだことを記録していく仕組みです。ビルドコマンド、デバッグの知見、アーキテクチャのメモ、コードスタイルの好み、作業の癖など。

**毎回何かを保存するわけではありません。** 将来の会話で役に立つかどうかを Claude が判断します。

### 保存場所

```
~/.claude/projects/<project>/memory/
├── MEMORY.md          # 索引。毎セッション読み込まれる
├── debugging.md       # デバッグパターンの詳細メモ
├── api-conventions.md # API 設計の決定事項
└── ...
```

- `<project>` は git リポジトリから導出されるので、**同じリポジトリの worktree はメモリを共有します**
- `MEMORY.md` の先頭 200 行（または 25KB）だけが毎セッション読み込まれます
- トピックファイルは必要になったときに Claude が読みに行きます
- **マシンローカル**です。他のマシンやクラウド環境とは共有されません

### 中身を見る・編集する

```text
/memory
```

すべてただの Markdown ファイルなので、読んで、直して、消せます。

### 明示的に覚えさせる

```text
pnpm を使って。npm は使わないで、と覚えておいて
```

```text
API のテストにはローカルの Redis インスタンスが必要だと覚えておいて
```

`CLAUDE.md` のほうに入れたいときは「これを CLAUDE.md に追加して」と伝えてください。

### 無効にする

- `/memory` のトグルから切り替え（`~/.claude/settings.json` の `autoMemoryEnabled` に保存される）
- プロジェクト単位: そのプロジェクトの設定に `{"autoMemoryEnabled": false}`
- 環境変数: `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`

## 6-8. 指示が守られないときのデバッグ

`CLAUDE.md` の内容は、システムプロンプトではなく**その後のユーザーメッセージとして渡されます。** Claude は読んで従おうとしますが、厳密な保証はありません。特に曖昧な指示や矛盾する指示では守られにくくなります。

### チェック手順

1. **`/context` を実行**して、**Memory files** に該当ファイルがあるか確認する
   → 無ければ Claude には見えていません。置き場所を見直してください（[6-3](#6-3-どこに置くか)）
2. **より具体的に書き直す**
   「コードをきれいに整形する」より「インデントは半角スペース 2 つ」
3. **矛盾する指示を探す**
   複数の `CLAUDE.md` や `.claude/rules/` で食い違っていないか
4. **ファイルが長すぎないか確認する**
   200 行を超えているなら削る、またはパススコープルールに移す

### それでもダメなとき

| 状況 | 対処 |
| --- | --- |
| 特定のタイミングで必ず実行させたい（コミット前、編集後など） | **フック**にする。シェルコマンドとして確実に実行される |
| 絶対に禁止したい操作がある | フックの `PreToolUse` でブロックする、または権限の `deny` ルール |
| 時々しか必要ない手順・知識 | **スキル**にする。必要なときだけ読み込まれ、コンテキストを圧迫しない |
| システムプロンプトのレベルで指示したい | `--append-system-prompt`（毎回渡す必要があるのでスクリプト向き） |

### `/compact` の後に指示が消えたように見える

プロジェクトルートの `CLAUDE.md` は圧縮後に**再読み込みされます**。サブディレクトリの `CLAUDE.md` は自動では再注入されず、そのディレクトリのファイルを次に読んだときに再読み込みされます。
会話の中だけで伝えた指示は消えるので、残したいなら `CLAUDE.md` に書いてください。

### ファイルが大きくなりすぎた

`/doctor` を実行すると、コミット済みの `CLAUDE.md` に対して削減案を提示してくれます。ディレクトリ構成・依存一覧・アーキテクチャ概要のような「コードから分かること」を削り、落とし穴・理由・デフォルトと異なる規約を残す方向で提案されます。

## 6-9. 組織全体で管理する（管理者向け）

### 全社共通の CLAUDE.md を配布する

管理ポリシーの場所（[6-3](#6-3-どこに置くか) の表）にファイルを置き、MDM・グループポリシー・Ansible などで各マシンに配布します。**このファイルは個人設定では除外できません。**

`managed-settings.json` の `claudeMd` キーに直接内容を書くこともできます。

```json
{
  "claudeMd": "コミット前に必ず `make lint` を実行すること。\nmain ブランチに直接プッシュしないこと。"
}
```

### 使い分け

| やりたいこと | どこに書くか |
| --- | --- |
| 特定のツール・コマンド・パスをブロックする | 管理設定の `permissions.deny` |
| サンドボックスを強制する | 管理設定の `sandbox.enabled` |
| 環境変数・API プロバイダのルーティング | 管理設定の `env` |
| コードスタイル・品質のガイドライン | 管理 CLAUDE.md |
| データの取り扱い・コンプライアンスの注意喚起 | 管理 CLAUDE.md |

**設定は技術的に強制され、CLAUDE.md は行動を誘導するもの**、という区別で考えてください。

### モノレポで他チームの CLAUDE.md を除外する

```json
{
  "claudeMdExcludes": [
    "**/monorepo/CLAUDE.md",
    "/home/user/monorepo/other-team/.claude/rules/**"
  ]
}
```

`.claude/settings.local.json` に書けば、自分のマシンだけの設定になります。
