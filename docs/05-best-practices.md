# 05. 効果的な使い方

> **この章でわかること**
> - Claude Code の性能を左右する「たった 1 つの制約」
> - 検証手段を与えることがなぜ最重要なのか
> - 探索 → 計画 → 実装 → コミット の進め方
> - よくある失敗パターンと、その直し方

この章の内容は、Anthropic 社内チームと多くの利用者の実践から得られたパターンです。**この章を読むと結果の質が明確に変わります。**

---

## 5-1. すべての土台: コンテキストウィンドウ

Claude Code のベストプラクティスのほとんどは、たった 1 つの制約から導かれます。

> **コンテキストウィンドウはすぐ埋まる。そして埋まるほど性能が落ちる。**

コンテキストウィンドウには、会話のすべて、読んだファイルの中身、実行したコマンドの出力が入ります。デバッグセッション 1 回、コードベースの探索 1 回で、数万トークンを消費することもあります。

いっぱいに近づくと、Claude は前の指示を「忘れ」たり、ミスが増えたりします。
**コンテキストは最も重要な管理対象リソースです。**

ここから先のプラクティスは、ほぼすべてこの制約への対処だと思って読んでください。

---

## 5-2. 【最重要】検証できる手段を与える

> Claude は「できたように見えた」ところで止まります。
> 実行できる合否判定が無いと、「できたように見える」が唯一の判断材料になり、**あなたが検証ループそのものになってしまいます。**

合否がはっきり出る手段を渡せば、ループは自分で閉じます。Claude が作業し、チェックを実行し、結果を読み、通るまで繰り返します。

### 「チェック」になるもの

- テストスイート
- ビルドの終了コード
- Lint
- 出力を期待値と比較するスクリプト
- ブラウザのスクリーンショットとデザインの比較

### プロンプトの書き方（Before / After）

| やり方 | Before | After |
| --- | --- | --- |
| **検証基準を渡す** | 「メールアドレスを検証する関数を実装して」 | 「validateEmail 関数を書いて。テストケース例: `user@example.com` は true、`invalid` は false、`user@.com` は false。実装後にテストを実行して」 |
| **UI は視覚的に検証させる** | 「ダッシュボードの見た目を良くして」 | 「[スクリーンショット] このデザイン通りに実装して。実装結果のスクリーンショットを撮って元と比較し、違いを列挙してから直して」 |
| **根本原因に対処させる** | 「ビルドが失敗する」 | 「ビルドがこのエラーで失敗する: [エラー貼り付け]。直してビルドが通ることを確認して。エラーを握りつぶすのではなく根本原因に対処して」 |

### 検証の「縛りの強さ」を選ぶ

| 方法 | やり方 | 強さ |
| --- | --- | --- |
| **プロンプトで頼む** | 「テストを実行して、通るまで直して」と同じメッセージ内で頼む | 手軽。今日から使える |
| **`/goal` で条件を設定** | 別の評価役が毎ターン条件を再チェックし、満たすまで作業を続けさせる | 中 |
| **Stop フックでゲートにする** | チェックをスクリプト化し、通るまでターンの終了をブロックする | 強い（決定論的） |
| **サブエージェントに検証させる** | 別のコンテキストのモデルに結果を反証させる | 作業者と採点者を分離できる |

**「できました」ではなく証拠を出させる。** 実行したコマンドとその出力、テスト結果、スクリーンショット。証拠を見るほうが、自分で再実行するより速いです。

## 5-3. 探索 → 計画 → 実装 → コミット

いきなりコードを書かせると、**間違った問題を解いてしまう**ことがあります。調査・計画と実装を分けましょう。

### ステップ 1: 探索（プランモード）

`Shift+Tab` でプランモードに入ります。Claude はファイルを読み、質問に答えますが、**変更はしません**。

```text
/src/auth を読んで、セッションとログインをどう扱っているか把握して。
シークレットの環境変数の管理方法も見て。
```

### ステップ 2: 計画

```text
Google OAuth を追加したい。どのファイルを変更する必要がある？
セッションのフローはどうなる？計画を立てて。
```

`Ctrl+G` を押すと、提示されたプランを自分のエディタで開いて直接編集できます。

### ステップ 3: 実装

プランモードを抜けて実装させます。

```text
立てた計画に沿って OAuth フローを実装して。
コールバックハンドラのテストも書いて、テストスイートを実行して、
失敗したら直して。
```

### ステップ 4: コミット

```text
分かりやすいメッセージでコミットして、PR を作って
```

### プランモードを使うべき / 使わないべき場面

| 使うべき | 使わないべき |
| --- | --- |
| アプローチに迷いがある | 差分を一文で説明できる |
| 複数ファイルにまたがる変更 | typo 修正、ログ 1 行追加、変数名の変更 |
| 触るコードに詳しくない | やることが明確で小さい |

**「差分を一文で説明できるなら、計画は飛ばしてよい」** が目安です。

## 5-4. 具体的な指示を書く

Claude は意図を推測できますが、心は読めません。ファイル名を挙げ、制約を伝え、お手本になるパターンを指し示してください。

| 方針 | Before | After |
| --- | --- | --- |
| **範囲を絞る** | 「foo.py にテストを追加して」 | 「foo.py の、ユーザーがログアウトしている場合のエッジケースのテストを書いて。モックは避けて」 |
| **情報源を指す** | 「なんで ExecutionFactory の API はこんな変な形なの？」 | 「ExecutionFactory の git 履歴を辿って、この API がこうなった経緯を要約して」 |
| **既存パターンを示す** | 「カレンダーウィジェットを追加して」 | 「ホーム画面の既存ウィジェットの実装を見てパターンを把握して。HotDogWidget.php が良い例。同じパターンでカレンダーウィジェットを実装して。既存の依存以外のライブラリは使わないで」 |
| **症状を説明する** | 「ログインのバグを直して」 | 「セッションタイムアウト後にログインが失敗する報告がある。src/auth/ の認証フロー、特にトークンリフレッシュを見て。まず再現する失敗テストを書いてから直して」 |

> **曖昧な指示が有効な場面もあります。**
> 「このファイルで改善できるところは？」のような問いかけは、自分では思いつかなかった観点を引き出せます。探索フェーズでは有効です。

## 5-5. コンテキストを積極的に管理する

### `/clear` を惜しまない

**関連のないタスクに移ったら `/clear`。** これが最も効果的な習慣です。

### 2回直して直らなければリセット

同じ問題で 2 回以上修正指示を出したなら、コンテキストは失敗した試行で汚れています。
`/clear` して、**そこまでで学んだことを盛り込んだより具体的なプロンプト**で仕切り直したほうが、ほぼ確実に速く済みます。

### 圧縮を使い分ける

| 方法 | 使いどころ |
| --- | --- |
| 自動コンパクション | 限界が近づくと自動で走る。重要なコードや決定は保持される |
| `/compact API の変更点を中心に残して` | 何を残すかを指定したいとき |
| `Esc` `Esc` → Summarize from here / up to here | 会話の一部だけを要約したいとき |
| `/clear` | 続きの文脈が不要なとき（最も安い。トークンを消費しない） |

`CLAUDE.md` に圧縮時の指示を書いておくこともできます。

```markdown
# 圧縮時の指示
コンパクトする際は、変更したファイルの一覧とテストコマンドを必ず残すこと
```

### 調査はサブエージェントに任せる

コンテキストが根本的な制約である以上、**サブエージェントは最も強力な道具の 1 つ**です。
サブエージェントは別のコンテキストウィンドウで動き、結果の要約だけを返します。

```text
サブエージェントを使って、認証システムのトークンリフレッシュの仕組みと、
再利用できる OAuth ユーティリティが既にあるかを調べて。
```

検証にも使えます。

```text
サブエージェントを使って、このコードのエッジケースをレビューして
```

### `/btw` で寄り道する

会話履歴に残さずに質問できます。ちょっとした確認でコンテキストを膨らませたくないときに。

## 5-6. 環境を整える（一度やれば毎回効く）

### `CLAUDE.md` を書く

毎セッション自動で読み込まれるファイルです。`/init` で雛形を生成できます。

**200 行以内に収めるのが目安。** 長すぎると重要なルールが埋もれ、Claude が半分無視するようになります。

| 書くべきこと | 書かないほうがよいこと |
| --- | --- |
| Claude が推測できないシェルコマンド | コードを読めば分かること |
| デフォルトと違うコードスタイル規約 | 一般的な言語の慣習 |
| テストの実行方法・使うテストランナー | 詳細な API 仕様（リンクで十分） |
| リポジトリの作法（ブランチ命名、PR 規約） | 頻繁に変わる情報 |
| プロジェクト固有のアーキテクチャ判断 | 長い説明やチュートリアル |
| 開発環境の癖（必須の環境変数など） | ファイルごとの説明 |
| 非自明な落とし穴 | 「きれいなコードを書く」のような自明な話 |

詳しくは [06 CLAUDE.md とメモリ](06-claude-md.md) を参照してください。

### 権限設定を整える

10 回目の承認では、もう本気で確認していません。以下のいずれかで承認疲れを減らします。

- **auto モード**: 別の分類モデルが危険な操作だけをブロック
- **許可リスト**: `npm run lint` や `git commit` など安全なものを事前承認
- **サンドボックス**: OS レベルでファイル・ネットワークを隔離

→ [07 権限とセキュリティ](07-permissions-security.md)

### CLI ツールを入れる

`gh`、`aws`、`gcloud`、`sentry-cli` などの CLI は、**外部サービスと連携する最もコンテキスト効率の良い方法**です。MCP サーバーと違い、ツール一覧の分のコンテキストを消費しません。

知らない CLI でも、こう頼めば使えるようになります。

```text
foo-cli-tool --help でこのツールの使い方を学んでから、A・B・C をやって
```

### スキル・フック・MCP を整備する

- **スキル**: 繰り返す手順を `/deploy` のようなコマンドにする
- **フック**: 「毎回必ず起きてほしいこと」を決定論的に保証する（編集後の自動フォーマットなど）
- **MCP**: 外部サービス（DB、Jira、Figma、Slack）に接続する

→ [08 拡張機能](08-extensions.md)

## 5-7. 並列で動かす

### 書き手 / レビュー役に分ける

新しいコンテキストのほうが、レビューの質は上がります。自分が書いたコードに引きずられないためです。

| セッション A（実装役） | セッション B（レビュー役） |
| --- | --- |
| `API エンドポイントにレートリミッターを実装して` | |
| | `@src/middleware/rateLimiter.ts の実装をレビューして。エッジケース、競合状態、既存ミドルウェアとの一貫性を見て` |
| `レビュー結果はこれ: [B の出力]。対応して` | |

テストでも同じことができます。片方にテストを書かせ、もう片方にそれを通すコードを書かせる、という進め方です。

### 並列実行の選択肢

| 方法 | 説明 |
| --- | --- |
| **git worktree** | `claude -w feature-auth` で隔離されたチェックアウトを作り、変更が衝突しない |
| **デスクトップアプリ** | 複数のローカルセッションを視覚的に管理（各セッションが独自の worktree） |
| **Web 版** | Anthropic 管理のクラウド VM 上で複数セッション |
| **エージェントチーム** | 複数セッションが共有タスクリストとメッセージで自動連携（実験的機能） |

→ [09 自動化とチーム利用](09-automation.md)

### 最後に「敵対的レビュー」を入れる

無人で長く動かすほど、独立したチェックの価値が上がります。

```text
サブエージェントを使って、レートリミッターの差分を PLAN.md と突き合わせてレビューして。
要件がすべて実装されているか、列挙したエッジケースにテストがあるか、
タスクのスコープ外が変更されていないかを確認して。
スタイルの好みではなく、抜け漏れだけを報告して。
```

> **注意**
> 「抜け漏れを探せ」と言われたレビュー役は、たとえ問題が無くても何かしら報告します。それが仕事だからです。
> すべての指摘を潰そうとすると過剰設計（不要な抽象化、防御的コード、起こり得ないケースのテスト）に陥ります。
> **「正しさか、明示した要件に影響する抜け漏れだけを報告して」** と伝え、残りは任意扱いにしましょう。

## 5-8. よくある失敗パターンと直し方

| パターン | 何が起きているか | 直し方 |
| --- | --- | --- |
| **なんでも1セッション** | 1つのタスクを始めて、途中で無関係な話をして、また戻る。コンテキストが無関係な情報だらけ | 無関係なタスクの間で `/clear` |
| **修正の無限ループ** | 間違い→指摘→まだ間違い→また指摘。失敗した試行でコンテキストが汚染される | 2回失敗したら `/clear` して、学んだことを盛り込んだプロンプトで再スタート |
| **CLAUDE.md 肥大化** | 長すぎて重要なルールがノイズに埋もれ、半分無視される | 容赦なく削る。指示が無くても正しくできることは消す。必ず守らせたいことはフックにする |
| **信じて検証しない** | もっともらしいがエッジケースを扱えていない実装ができあがる | 必ず検証手段（テスト、スクリプト、スクリーンショット）を渡す。検証できないものは出荷しない |
| **無限の探索** | 範囲を決めずに「調査して」と頼み、何百ファイルも読んでコンテキストが埋まる | 調査範囲を絞る、またはサブエージェントに任せる |

## 5-9. 最後に: 自分の勘を育てる

ここに書いたパターンは絶対のルールではありません。

- 1 つの複雑な問題に深く潜っていて、履歴に価値があるなら、コンテキストを溜めたままでよいこともあります
- 探索的なタスクなら、計画を飛ばして走らせたほうが良いこともあります
- 制約をかける前にどう解釈するか見たいなら、あえて曖昧に頼むのが正解のこともあります

**うまくいったときに、何をしたのかを意識してください。** プロンプトの構造、渡したコンテキスト、使っていたモード。逆にうまくいかなかったときは、なぜかを考えてください。コンテキストがノイジーだったのか、指示が曖昧だったのか、タスクが一度に扱うには大きすぎたのか。
