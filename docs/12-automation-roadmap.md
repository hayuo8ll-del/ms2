# 12. 業務自動化ロードマップ

> **この章でわかること**
> - どの業務から自動化に着手すべきかの選び方
> - 「手作業 → 無人実行」までを 5 段階で進めるロードマップ
> - 各段階で作る成果物（`CLAUDE.md`／スキル／フック／CI／Routines）と完了条件
> - 業務パターン別の具体的なレシピ
> - 失敗するパターンと、運用に乗せてからの回し方

08 章・09 章が「**どんな機能があるか**」の説明なのに対し、この章は
「**どの順番で、何から手を付けるか**」の進め方をまとめたものです。

---

## 12-0. 全体像

自動化は一足飛びには進みません。**同じ作業を、毎回少しずつ人手から剥がしていく**のが基本です。

```
Phase 0  土台        Claude Code が「検証できる」状態を作る
   ↓
Phase 1  手動反復    自分でやりながら、手順を言語化する
   ↓
Phase 2  資産化      手順をスキル／サブエージェントとして固定する
   ↓
Phase 3  無人実行    claude -p でスクリプトから呼べるようにする
   ↓
Phase 4  自動起動    CI・Routines・フックでイベントや時刻から起動する
   ↓
Phase 5  運用        精度・コスト・失敗率を見ながら維持・改善する
```

各フェーズの目安は次のとおりです。**1 業務ごとに Phase 1 → 5 を回します。**
複数業務を同時に Phase 5 まで持っていこうとすると、まず失敗します。

| Phase | 期間の目安 | 主な成果物 | 完了条件 |
| --- | --- | --- | --- |
| 0 土台 | 1〜3 日 | `CLAUDE.md`、`.claude/settings.json`、テスト／Lint コマンド | 新しいセッションで「いつもの説明」をしなくて済む |
| 1 手動反復 | 1〜2 週 | 手順メモ（プロンプトの原文） | 同じプロンプトで 3 回連続、手直しなしで完了する |
| 2 資産化 | 1〜3 日 | `.claude/skills/<name>/SKILL.md` | `/コマンド名` の一言で同じ結果になる |
| 3 無人実行 | 1〜3 日 | シェルスクリプト（`claude -p`） | 承認ボタンを一度も押さずに完了する |
| 4 自動起動 | 1〜5 日 | GitHub Actions／Routines／フック | 人が起動しなくても走り、結果が通知される |
| 5 運用 | 継続 | 実行ログ、成功率、コストの記録 | 「止まっても誰かが気付く」状態になっている |

## 12-1. 何を自動化するか決める

### ステップ 1: 1 週間、自分の作業を棚卸しする

難しく考えず、**「今週やった作業」を箇条書きにする**ところから始めます。Claude Code に手伝わせても構いません。

```text
直近 2 週間のコミットログとブランチ名を見て、繰り返し発生している作業の種類を分類して。
それぞれ何回発生したかも数えて
```

### ステップ 2: 選定基準にかける

自動化の候補は、次の 4 つを満たすものから選びます。

| 基準 | 具体的には |
| --- | --- |
| **頻度が高い** | 週 1 回以上。月 1 回の作業は自動化コストを回収できないことが多い |
| **手順が決まっている** | 「その時々で判断が変わる」作業は Phase 2 で詰まる |
| **正解を機械的に判定できる** | テストが通る／Lint が通る／JSON が壊れていない、など |
| **失敗しても壊滅しない** | 本番 DB の変更、課金処理、外部への送信は最後に回す |

**特に 3 つめが決定的です。** 検証手段のない業務を自動化すると、
「それっぽい結果が返るが正しいかは誰にも分からない」という一番厄介な状態になります。
→ [05-2 検証できる手段を与える](05-best-practices.md)

### ステップ 3: 費用対効果を雑に見積もる

```
削減時間 = （1 回あたりの所要時間 × 実行頻度 × 期間）− 自動化にかけた時間 − 運用の手間
```

数字を厳密に出す必要はありません。**「3 か月で元が取れないなら後回し」**くらいの粗さで十分です。

### 着手順のおすすめ

1. **読む・調べる系**（ログ調査、コードベースの説明、影響範囲の洗い出し）
   — 何も壊さないので、権限設定が緩くても安全。最初の 1 本に最適
2. **書くけれど検証できる系**（テスト追加、Lint 修正、型付け、ドキュメント同期）
   — テストが関門になるので暴走しても気付ける
3. **人の目が入る系**（PR レビューコメント、Issue トリアージ）
   — 出力が提案止まりで、採用の判断は人がする
4. **外部に影響する系**（リリース、デプロイ、通知の送信）
   — 上の 3 つが安定してから

## 12-2. Phase 0 — 土台を作る

**この段階を飛ばすと、以降のすべてが不安定になります。**

### やること

| # | やること | 参照 |
| --- | --- | --- |
| 1 | `/init` で `CLAUDE.md` を作り、ビルド・テスト・Lint のコマンドを書く | [06 CLAUDE.md とメモリ](06-claude-md.md) |
| 2 | テスト／Lint が **1 コマンドで走る**ようにする | [05-2](05-best-practices.md) |
| 3 | 権限の許可リストを `.claude/settings.json` に書いてコミットする | [07 権限とセキュリティ](07-permissions-security.md) |
| 4 | よく使う外部ツール（`gh` など）を入れる | [02-7](02-setup.md) |

### `CLAUDE.md` に最低限書くこと

```markdown
# コマンド
- テスト: npm test
- 型チェック: npm run typecheck
- Lint: npm run lint（修正は npm run lint -- --fix）

# 作業ルール
- 変更後は必ず npm test と npm run lint を実行する
- src/generated/ は自動生成なので直接編集しない
- コミットメッセージは日本語、prefix は feat/fix/docs/chore
```

### 権限の初期設定

無人実行に進む前提なら、**許可するコマンドは具体的に書きます。**

```json
{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Bash(npm run lint*)",
      "Bash(git add:*)",
      "Bash(git commit:*)"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ]
  }
}
```

> `Bash(*)` のような広すぎる許可は、Phase 4 で「無人で何でも実行できる状態」に直結します。
> 最初から絞っておくほうが、後で緩めるより安全です。

### 完了条件

新しいセッションで `/clear` してから作業を頼んだとき、
**プロジェクトの説明を毎回やり直さなくて済む**状態になっていること。

## 12-3. Phase 1 — 手動で繰り返し、手順を言語化する

いきなりスキルを書かないでください。**まず 3〜5 回、自分で手動でやります。**

### 進め方

1. 対象業務を、いつもどおり Claude Code に頼む
2. うまくいかなかった点をメモする（何を追加で説明したか）
3. その説明を**次回のプロンプトに最初から入れる**
4. 手直しが要らなくなるまで繰り返す

### 記録するもの

```text
# 業務名: 週次の依存パッケージ監査

## プロンプト（最新版）
npm outdated と npm audit を実行して、次の形式で報告して:
- 緊急（脆弱性あり）: パッケージ名 / 現在 → 推奨 / CVE
- 通常（メジャー更新あり）: パッケージ名 / 現在 → 最新
破壊的変更がありそうなものには理由を 1 行添えて。修正はまだしないこと。

## 必要な権限
Bash(npm outdated), Bash(npm audit)

## 失敗パターン
- 「更新して」まで書くと勝手に package.json を書き換えるので、報告のみと明示する
- private レジストリのパッケージは outdated に出ないので注意
```

### 完了条件

**同じプロンプトで 3 回連続、手直しなしで期待した結果になる。**
ここが安定していない業務を Phase 2 に進めても、スキルの中で同じブレが起きるだけです。

## 12-4. Phase 2 — 手順を資産化する

Phase 1 のメモを、**チーム全員が呼び出せる形**に変換します。

### どれを使うか

| 作るもの | 向いているもの | 参照 |
| --- | --- | --- |
| **スキル** | 手順が決まった作業。`/名前` で呼べる | [08-2 スキル](08-extensions.md) |
| **`.claude/rules/`** | 特定のディレクトリを触るときだけ効かせたいルール | [06-6](06-claude-md.md) |
| **サブエージェント** | 調査・レビューなど、本体の文脈を汚したくない作業 | [08-5 サブエージェント](08-extensions.md) |
| **MCP** | 外部サービス（Jira、DB、Slack）のデータが必要な作業 | [08-4 MCP](08-extensions.md) |

### スキルにする

```markdown
---
name: dep-audit
description: 依存パッケージの脆弱性とメジャー更新を監査して報告する。週次の依存監査や、npm audit の結果をまとめたいときに使う。
---

# 依存パッケージ監査

## 手順
1. `npm outdated --json` と `npm audit --json` を実行する
2. 結果を次の形式でまとめる
   - 緊急（脆弱性あり）: パッケージ名 / 現在 → 推奨 / CVE / 深刻度
   - 通常（メジャー更新あり）: パッケージ名 / 現在 → 最新 / 破壊的変更の有無
3. `reports/deps-YYYY-MM-DD.md` に書き出す

## 制約
- package.json / package-lock.json は変更しない（報告のみ）
- private レジストリのパッケージは対象外である旨を明記する
```

`.claude/skills/dep-audit/SKILL.md` に置き、**git にコミットして共有します。**

> `description` は「何をするか」だけでなく**「いつ使うか」**まで書いてください。
> ここが曖昧だと、Claude がスキルを呼ぶべき場面で呼びません。

### 完了条件

```text
/dep-audit
```

の一言で、Phase 1 と同じ品質の結果が出ること。

## 12-5. Phase 3 — 無人で実行できるようにする

対話なしで完了する状態にします。**ここからが本当の「自動化」です。**

### 基本形

```bash
claude -p "/dep-audit を実行して、結果を reports/ に保存して" \
  --allowedTools "Read,Write,Bash(npm outdated*),Bash(npm audit*)" \
  --permission-mode dontAsk \
  --max-turns 20 \
  --max-budget-usd 2.00
```

| フラグ | 無人実行での役割 |
| --- | --- |
| `--allowedTools` | 承認待ちで止まらないようにする。**列挙したもの以外は使えない** |
| `--permission-mode dontAsk` | 事前承認以外は自動拒否。無人実行の既定にすべきモード |
| `--max-turns` | 無限ループの保険 |
| `--max-budget-usd` | 暴走時のコスト上限 |

→ 詳細は [09-1 非対話モード](09-automation.md)

### 結果を機械的に扱う

```bash
result=$(claude -p "変更されたファイルに脆弱性がないか確認して。問題なければ OK のみ、あれば FAIL と理由を返して" \
  --allowedTools "Read,Bash(git diff*)" \
  --permission-mode dontAsk \
  --output-format json | jq -r '.result')

case "$result" in
  OK*) echo "問題なし" ;;
  *)   echo "要確認: $result"; exit 1 ;;
esac
```

**出力形式をプロンプトで固定し、`--output-format json` で受け取る。** これが後続処理を安定させるコツです。

### 安全に運用するための型

1. **まずドライランを作る** — 変更系は最初「提案だけ出す」モードで動かす
2. **書き込み先を隔離する** — 直接コミットではなく、ブランチや `reports/` に出す
3. **小さく試す** — 全件ではなく 2〜3 件で流し、想定外を先に潰す（[09-2 ファンアウト](09-automation.md)）
4. **失敗を検出できるようにする** — 終了コードか出力の固定文字列で判定する

### 完了条件

**承認ボタンを一度も押さずに、スクリプトが最後まで走り切る。**

## 12-6. Phase 4 — 自動で起動させる

人が叩かなくても走る状態にします。**起動のきっかけは 3 種類**です。

| きっかけ | 手段 | 例 |
| --- | --- | --- |
| **時刻** | Routines（`/schedule`）、デスクトップの定期タスク、cron | 毎朝の PR サマリ、週次の依存監査 |
| **イベント** | GitHub Actions、Auto-fix、Webhook | PR 作成時のレビュー、CI 失敗時の修正 |
| **操作** | フック | 編集後の整形、コミット前の Lint |

### 時刻で起動する（Routines）

```text
/schedule
```

Anthropic 管理のインフラで動くため、**PC の電源が入っていなくても実行されます。**
「毎週月曜 9:00 に依存監査を実行して、結果を Issue に書く」といった用途に向いています。

現在のセッション内で簡易的にポーリングしたいだけなら `/loop` を使います。

```text
/loop 30m /pr-feedback
```

> `/loop` はセッションのコンテキストを毎回送るため、放置するとトークンを消費し続けます。
> **長時間の定期実行は Routines を使ってください。** → [09-6 定期実行](09-automation.md)

### イベントで起動する（GitHub Actions）

```text
/install-github-app
```

導入しやすい順は次のとおりです。

1. **PR の自動レビュー**（コメントするだけ／破壊的でない）
2. **Issue のトリアージ**（ラベル付け・重複チェック）
3. **`@claude` メンションでの実装依頼**
4. **Auto-fix**（CI 失敗やレビューコメントへの自動対応）

> ⚠️ Atlantis や `issue_comment` で動くワークフローがあるリポジトリでは、
> **Claude のコメントが別の自動化を起動する**ことがあります。有効化前に確認してください。
> → [09-4 CI / CD 連携](09-automation.md)

### 操作で起動する（フック）

「毎回必ず」やらせたいことは、お願い（`CLAUDE.md`）ではなく**フック**にします。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
        ]
      }
    ]
  }
}
```

→ [08-3 フック](08-extensions.md)

### 完了条件

**人が起動しなくても走り、結果が人の見える場所（Issue／Slack／レポート）に届く。**

## 12-7. Phase 5 — 運用に乗せる

自動化は作った時点が最高精度で、**放置すると必ず劣化します**（依存の更新、仕様変更、プロンプトの陳腐化）。

### 見る指標

| 指標 | 見方 | 危険信号 |
| --- | --- | --- |
| **成功率** | 実行回数のうち、人の手直しが不要だった割合 | 8 割を切ったらプロンプトかスキルを見直す |
| **コスト** | 1 実行あたりの金額、月合計 | 想定の 2 倍を超えたらスコープが広すぎる |
| **所要時間** | 実行時間の推移 | 伸び続けているならコンテキストが膨らんでいる |
| **無視率** | 出力を誰も読んでいない | 自動化そのものを止める判断材料 |

使用状況の確認方法は [09-7](09-automation.md) と
[10-5 コストとトークンを節約する](10-troubleshooting.md) を参照してください。

### 定期的にやること

- **月 1 回**: 失敗した実行のログを 3 件読み、共通する原因をスキルに反映する
- **四半期に 1 回**: 出力を誰も見ていない自動化を**止める**
- **バージョン更新時**: `claude --version` を上げたら、無人実行のスクリプトを一度手で流す

### 止め方も決めておく

無人実行は「壊れても誰も気付かない」のが最大のリスクです。

- 失敗時に通知が飛ぶようにする（Actions の失敗通知、Routines の結果通知）
- **一定回数連続で失敗したら自動で止める**（スクリプト側でカウントする）
- 誰が面倒を見るかを決める（担当者不在の自動化は必ず腐ります）

## 12-8. 業務パターン別レシピ

| 業務 | Phase 2 で作るもの | Phase 4 の起動 | 検証手段 |
| --- | --- | --- | --- |
| PR レビュー | レビュー観点スキル＋サブエージェント | GitHub Actions（PR 作成時） | 人がコメントを採否 |
| Issue トリアージ | 分類ルールを書いたスキル | GitHub Actions（Issue 作成時） | ラベルの妥当性を目視 |
| 依存パッケージ監査 | `dep-audit` スキル | Routines（週次） | `npm audit` の終了コード |
| CI 失敗の一次調査 | ログ要約スキル | Actions の失敗時 | 原因の指摘が当たったか |
| テスト追加 | テスト規約を書いたスキル | 手動 or `claude -p` のバッチ | テストが通る／カバレッジ |
| ドキュメント同期 | 対応表を書いたスキル | PR マージ後 | ドキュメントのリンク切れ検査 |
| 定期レポート作成 | 集計手順スキル | Routines（週次・月次） | 出力フォーマットの検査 |
| ログ調査 | 抽出条件を書いたスキル | 手動（`claude -p`） | 抽出件数の妥当性 |
| 大量ファイルの一括変換 | 変換手順スキル | シェルの for ループ | ビルド／テスト |

### 例 1: 毎朝の PR サマリ（Routines）

```text
open な PR をすべて確認して、次の形式で Issue #42 にコメントして:
- レビュー待ち 3 日以上: PR 番号 / タイトル / 担当
- CI 失敗中: PR 番号 / 失敗しているジョブ名
- マージ可能: PR 番号 / タイトル
該当なしのカテゴリは「なし」と書くこと。PR の変更は一切しないこと。
```

`/schedule` で平日 9:00 に登録します。**「変更しない」を明記する**のが重要です。

### 例 2: 大量ファイルの一括変換（ファンアウト）

```bash
# ステップ 1: 対象を洗い出す（対話で）
#   「移行が必要なファイルを列挙して files.txt に書き出して」

# ステップ 2: まず 3 件で試す
head -3 files.txt | while read -r f; do
  claude -p "$f を新しい API に移行して。完了したら DONE、判断に迷ったら SKIP と理由を返して" \
    --allowedTools "Read,Edit,Bash(npm test)" \
    --permission-mode dontAsk \
    --max-turns 15
done

# ステップ 3: 問題なければ全件、1 件ずつコミット
while read -r f; do
  claude -p "$f を新しい API に移行して。テストが通ったらコミットして" \
    --allowedTools "Read,Edit,Bash(npm test),Bash(git add:*),Bash(git commit:*)" \
    --permission-mode dontAsk \
    --max-turns 15 --max-budget-usd 1.00
done < files.txt
```

**1 ファイル 1 コミット**にしておくと、後から問題のあった変更だけを戻せます。

### 例 3: コミット前の必須チェック（フック）

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/block-secret-commit.sh" }
        ]
      }
    ]
  }
}
```

「認証情報を含むコミットを止める」のような**絶対に破られたくないルール**は、
指示ではなくフックで**決定論的に**止めます。

## 12-9. うまくいかないパターン

| パターン | 何が起きるか | 対処 |
| --- | --- | --- |
| **検証手段のない業務から始める** | 正しいのか誰も判断できない出力が量産される | テスト・スキーマ検査・件数チェックを先に用意する |
| **Phase 1 を飛ばしてスキルを書く** | スキルの中で毎回違う結果が出る | 手動で 3 回安定してから資産化する |
| **いきなり `bypassPermissions`** | 想定外のコマンドが無人で走る | `dontAsk` ＋ `--allowedTools` の列挙に置き換える |
| **1 スキルに手順を詰め込みすぎる** | 途中で文脈が溢れて後半が雑になる | 業務を分割し、スキルも分ける |
| **出力形式を決めていない** | 後続のスクリプトが壊れる | 形式をプロンプトで固定し `--output-format json` で受ける |
| **通知先が人の目に入らない** | 壊れても気付かない | Issue・Slack など普段見る場所に出す |
| **全社展開を最初にやる** | 誰も使わない仕組みが残る | 1 人 1 業務で成功させてから広げる |
| **`/loop` で長時間放置** | アイドル中もトークンを消費する | Routines に移す |

### 1〜2 週目: 土台（Phase 0）

- [ ] `/init` で `CLAUDE.md` を作成し、コミットした
- [ ] テスト・Lint が 1 コマンドで走る
- [ ] `.claude/settings.json` に許可／拒否ルールを書いてコミットした

- [ ] 手動で 3 回、手直しなしで完了した
