# 13. 活用事例（業務システム・社内ツール）

> **この章でわかること**
> - 業務システム・社内ツールならではの前提と、そこでの Claude Code の効かせ方
> - テスト作成・障害調査の具体的な進め方
> - ドキュメント作成・定型作業を自動化する手順
> - 本番データや機微情報を扱うときの線引き

ここに載せているのは、**業務システムや社内ツールの開発・保守でそのまま使える一般的なワークフロー**です。特定の組織の情報は含んでいません。自分の環境に合わせて、ファイル名やコマンドを置き換えて使ってください。

---

## 13-1. 業務システムならではの前提

Web サービスの新規開発と違い、業務システム・社内ツールの現場には固有の事情があります。**Claude Code の効かせどころもそこに合わせて変わります。**

| よくある前提 | Claude Code をどう効かせるか |
| --- | --- |
| **テストが薄い、または無い** | まずテストを足すこと自体を任せる。以降のすべての作業の土台になる |
| **仕様がドキュメント化されていない** | コードから仕様を復元させる。人が読む資料の形で残す |
| **作った人がもういない** | 変更の影響範囲を調べさせてから触る |
| **止められない・壊せない** | プランモードで先に計画を確認。権限は絞る |
| **同じ手作業が毎月ある** | スキル化して誰が実行しても同じ手順になるようにする |
| **技術スタックが古い** | 「既存のやり方に合わせて」と明示する。最新の流儀を持ち込ませない |

> **最初に効く一手**
> テストが無いコードベースなら、**まず「テストを書く」作業から始めてください。**
> [05 効果的な使い方](05-best-practices.md) で述べたとおり、Claude Code は検証手段があるかどうかで結果の質が大きく変わります。テストを足すことは、その後のすべての作業への投資になります。

## 13-2. 事例 A: テストが無いコードにテストを足す

### 課題

長年動いているが、テストが無い。触るのが怖い。だが直さないといけない。

### 進め方

**ステップ 1: 現状を把握させる**

```text
このリポジトリのテスト状況を調べて。
どのディレクトリにテストがあり、どのモジュールにテストが無いかを一覧にして。
テストの実行方法と、使っているテストフレームワークも教えて。
```

**ステップ 2: 1 ファイルだけで型を作る**

いきなり全体に広げず、**1 つのモジュールで「良いテストの形」を確定させます。**

```text
src/billing/calculator.py にユニットテストを書いて。

- 既存の tests/ のスタイルに合わせて
- 外部 I/O はモックせず、純粋な計算ロジックだけを対象にして
- 正常系だけでなく、境界値（0円、上限額、マイナス）も入れて
- 書いたら実行して、通ることを確認して
```

できたテストを**自分でレビューしてください。** ここで形が決まれば、あとは同じ形で量産できます。

**ステップ 3: 型が決まったらスキルにする**

```text
今書いたテストの方針をスキルにして。
.claude/skills/add-tests/SKILL.md として、
対象ファイルを引数で受け取れる形にして。
```

**ステップ 4: 残りに広げる**

```text
/add-tests src/billing/invoice.py
```

大量にあるなら、非対話モードでまとめて流せます。

```bash
for f in $(cat untested_files.txt); do
  claude -p "$f にユニットテストを書いて実行して。通ったら OK、失敗したら FAIL とだけ返して" \
    --allowedTools "Read,Edit,Write,Bash(pytest *)" \
    --max-turns 15
done
```

### 効いたポイント

- **いきなり全体に広げない。** 1 ファイルで形を確定させてから量産する
- **「既存のスタイルに合わせて」を必ず添える。** 放っておくと最新の流儀で書かれ、既存テストと不揃いになる
- **実行まで頼む。** 「書いて」だけだと、通らないテストができあがることがある

## 13-3. 事例 B: 障害調査

### 課題

本番で問題が起きた。ログはあるが量が多い。原因の当たりが付かない。

### 進め方

**ステップ 1: ログを渡して当たりを付けさせる**

ログはそのまま貼らず、**パイプで渡す**とコンテキストを節約できます。

```bash
grep -i error app.log | tail -200 | claude -p "このログから異常のパターンを抽出して。時系列と発生頻度も整理して"
```

対話セッションなら、シェルモードが便利です。

```text
!grep -c ERROR /var/log/app/*.log
```

**ステップ 2: 仮説をコードで裏取りさせる**

```text
このスタックトレースの発生箇所を特定して。
呼び出し元を辿って、どういう入力のときにこの経路に入るかを説明して。

[スタックトレースを貼り付け]
```

範囲が広いときはサブエージェントに任せます。**大量のファイルを読んでも、メインの会話は要約だけで済みます。**

```text
サブエージェントを使って、この例外が発生しうる入力パターンを洗い出して。
結論と根拠のファイル・行番号だけ報告して。
```

**ステップ 3: 再現テストを書かせる**

ここが最重要です。**再現できれば、直ったかどうかを機械が判定できます。**

```text
特定した原因を再現する失敗テストを書いて。
まず「失敗すること」を確認してから見せて。
```

**ステップ 4: 直して、通ることを確認させる**

```text
このテストが通るように直して。
エラーを握りつぶすのではなく根本原因に対処して。
既存のテストが全部通ることも確認して。
```

**ステップ 5: 記録を残す**

```text
今回の障害について、以下をまとめて docs/incidents/ に書いて。
- 事象と影響範囲
- 根本原因
- 実施した修正
- 再発防止のために追加したテスト
```

### 効いたポイント

- **ログは全文を読ませない。** `grep` や `tail` で絞ってから渡す。フックで前処理する手もあります（[08-3 フック](08-extensions.md#hooks)）
- **「再現テストを先に」が決定打。** これがあるかないかで修正の確度がまるで違います
- **調査はサブエージェントに。** メインの会話をログの断片で埋めない

## 13-4. 事例 C: 仕様が失われたコードのドキュメント化

### 課題

動いているが、なぜそうなっているか誰も説明できない。改修のたびに調査からやり直している。

### 進め方

**ステップ 1: 範囲を区切って読ませる**

「全部ドキュメント化して」は失敗します。**モジュール単位で区切ってください。**

```text
src/approval/ の承認フローを読んで、以下を docs/specs/approval-flow.md にまとめて。

- 承認の状態遷移（どの状態からどの状態に、何を条件に移るか）
- 各状態で通知が飛ぶ相手
- 差し戻し・取り下げの扱い
- コードから読み取れない前提があれば「要確認」として列挙して

図が有効なら Mermaid で入れて。
```

**「要確認」として列挙して** を入れるのが効きます。Claude が推測で埋めた箇所と、コードから確定した箇所を区別できます。

**ステップ 2: git の履歴から経緯を補う**

```text
この分岐がなぜ追加されたのか、git log と git blame から調べて。
関連するコミットメッセージと、そこから読み取れる背景を要約して。
```

**ステップ 3: 人が確認して確定させる**

「要確認」の項目を、有識者に聞くなり実機で確かめるなりして埋めます。**ここは人の仕事です。**

**ステップ 4: CLAUDE.md に要点だけ書く**

```markdown
# 承認フロー
- 状態遷移の詳細は docs/specs/approval-flow.md を参照
- 「取り下げ」は申請者のみ可能。承認者はできない（よく間違える）
```

詳細はドキュメント、**間違えやすい点だけを CLAUDE.md に**。以降のセッションで同じ間違いを繰り返さなくなります。

### 効いたポイント

- **範囲を区切る。** モジュール単位、機能単位で
- **推測と事実を分けさせる。** 「要確認」ラベルを必須にする
- **成果物は人が読む形に。** Claude のためだけでなく、チームの資産になります

## 13-5. 事例 D: 定型作業をスキルにする

### 課題

毎月・毎リリースで同じ手順を踏んでいる。手順書はあるが、人によって解釈が違う。

### 進め方

**ステップ 1: まず 1 回、会話で通す**

いきなりスキルを書かず、**手作業を Claude と一緒に 1 回やってみます。** ここで手順の抜けが見つかります。

**ステップ 2: 通った手順をスキルにさせる**

```text
今やった手順をスキルにして。
.claude/skills/monthly-report/SKILL.md として作って。
勝手に実行されると困るので、手動起動のみにして。
```

生成されるのはこういうファイルです。

```markdown
---
name: monthly-report
description: 月次の利用状況レポートを生成する
disable-model-invocation: true
---

月次レポートを作成する: $ARGUMENTS（対象年月、例: 2026-08）

1. `scripts/export_usage.sh $ARGUMENTS` で利用ログを抽出する
2. 抽出結果の件数を確認し、前月比で 50% 以上増減していたら警告する
3. reports/template.md の形式に沿って集計表を作る
4. 前月のレポートと比較し、特筆すべき変化があれば「所感」に書く
5. reports/YYYY-MM.md として保存する
6. 生成したファイルの差分を表示して、確認を求める
```

**ステップ 3: 使う**

```text
/monthly-report 2026-08
```

### 副作用のある作業には必ず手動起動を

デプロイ、メール送信、データ更新のように**勝手に実行されたら困るものは、`disable-model-invocation: true` を必ず付けてください。** Claude が自分の判断で実行することがなくなり、コンテキストの消費もゼロになります。

### さらに: 絶対に守らせたい手順はフックにする

「コミット前に必ず Lint」「`migrations/` は編集禁止」のような**破ってほしくないルールは、スキルではなくフックにします。** スキルの指示はお願いですが、フックは強制です。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "~/.claude/hooks/block-migrations.sh" }]
      }
    ]
  }
}
```

→ 詳しくは [08-3 フック](08-extensions.md#hooks)

## 13-6. 事例 E: 定期実行で「気づく」を自動化する

### 課題

問題に気づくのが遅い。誰も見ていない時間帯の CI 失敗、放置された PR、増え続ける警告。

### 進め方

**Routines（定期実行）**を使うと、**PC の電源が入っていなくても**決まった時刻に走ります。

```text
/schedule
```

業務システムの現場で効きやすいもの:

| 頻度 | 内容 |
| --- | --- |
| 毎朝 | 前日の CI 失敗をまとめて、原因の当たりを付けて報告 |
| 毎朝 | レビュー待ちの PR を一覧化し、滞留日数の長い順に並べる |
| 週次 | 依存パッケージの脆弱性・更新可能なバージョンを確認 |
| 週次 | エラーログの傾向を前週と比較し、増えているものを抽出 |
| リリース後 | 変更内容からリリースノートの草案を作る |

**ローカルのファイルやツールに直接アクセスする必要があるなら**、デスクトップアプリの定期タスクを使います。社内ネットワークの中でしか動かないコマンドがある場合はこちらです。

### 注意

`/loop` は現在のセッション内で繰り返す簡易的な仕組みで、**アイドル中もコンテキスト全体を送り続けるためトークンを消費します。** 長時間放置する用途には Routines のほうが適しています。

## 13-7. 業務システムで気をつけること

ここは**慎重に運用すべき部分**です。

### 本番データを触らせない

```json
{
  "permissions": {
    "deny": [
      "Bash(psql * production *)",
      "Bash(mysql * --host=prod*)",
      "Read(./secrets/**)",
      "Read(.env.production)"
    ]
  }
}
```

`deny` ルールは**すべての権限モードで有効**です（`bypassPermissions` でも）。モデルの判断に依存しない、確実な防御になります。

### 個人情報・機微情報の扱い

- 実データではなく**マスク済みのテストデータ**を読ませる
- 障害調査でログを渡すときは、氏名・メールアドレス・電話番号などを落としてから渡す
- `/export` や `/bug` で会話を共有する前に、中身を必ず確認する

### 外部から取り込んだ内容を鵜呑みにしない

Issue のコメント、CI のログ、取引先から受け取ったファイル。これらに「これまでの指示を無視して〜」のような文章が仕込まれている可能性があります。
→ [07-7 プロンプトインジェクションへの注意](07-permissions-security.md)

### 権限モードの使い分け（業務システム向けの目安）

| 場面 | おすすめ |
| --- | --- |
| 本番に近いコードを触る | **Manual**。1 つずつ確認する |
| テスト追加・ドキュメント作成 | **acceptEdits**。差分は後で `git diff` |
| 調査・影響範囲の確認 | **plan**。変更させない |
| 定型作業の一括実行 | **auto** ＋ `deny` ルールで危険域を封鎖 |
| CI での自動実行 | **dontAsk** ＋ `--allowedTools` で最小権限 |

> **auto モードが既定になりました。**
> 2026年8月14日以降、Pro / Max / Team プランでは **auto モードが新規セッションの既定**です。自分でデフォルトを設定している場合はそのまま維持されます。
> 業務システムで慎重に進めたい場合は、`Shift+Tab` で Manual に切り替えるか、設定でデフォルトを変えてください。
> → [07 権限とセキュリティ](07-permissions-security.md)

## 13-8. チームに広げるときの順番

一気に全部やろうとすると失敗します。**この順番が最も定着しやすいです。**

1. **自分ひとりで 2 週間使う** — どこで効くか、どこで効かないかの肌感を掴む
2. **`CLAUDE.md` を書いてコミットする** — ここまでで得た「毎回説明していること」を集約する
3. **テストを増やす** — 以降のすべての作業の精度が上がる
4. **定型作業を 1 つスキル化する** — 効果が目に見えるものを選ぶ
5. **権限方針をチームで決める** — `.claude/settings.json` に書いてコミット
6. **必ず守らせたいルールをフックにする** — 人によるばらつきを消す
7. **CI に組み込む** — PR の自動レビューから始めるのが入りやすい

→ 詳しくは [09-7 チーム導入のすすめ方](09-automation.md)
