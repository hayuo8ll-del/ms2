# 07. 権限とセキュリティ

> **この章でわかること**
> - 権限モードの違いと選び方
> - 承認の回数を減らす 3 つの方法
> - 保護されているパスと、絶対に auto 承認されない操作
> - 機密情報の扱いとプロンプトインジェクションへの注意

---

## 7-1. 基本の考え方

Claude Code がファイルを編集する、コマンドを実行する、ネットワークにアクセスするとき、**デフォルトでは毎回あなたに確認します。**

安全ですが、面倒でもあります。10 回目の承認ではもう本気で読んでいません。ただクリックしているだけです。
そこで、**「どこまで自動で任せ、どこで止まるか」を自分で決められる仕組み** が用意されています。

---

## 7-2. 権限モード

### 一覧

| モード | 確認なしで実行されること | 向いている場面 |
| --- | --- | --- |
| `default`（**Manual**） | 読み取りのみ | 使い始め、慎重に進めたい作業 |
| `acceptEdits` | 読み取り＋ファイル編集＋基本的なファイル操作コマンド（`mkdir`, `touch`, `mv`, `cp` など） | 差分を後でまとめて確認する進め方 |
| `plan` | 読み取りのみ（編集はブロック） | 変更前にコードベースを調べる |
| `auto` | ほぼすべて（バックグラウンドの安全チェック付き） | 長い作業、承認疲れを避けたいとき |
| `dontAsk` | 事前承認したツールのみ | CI・スクリプトなど、入力できない環境 |
| `bypassPermissions` | すべて | **隔離されたコンテナ・VM 専用** |

> **名前について**
> 「毎回確認するモード」は UI 上 **Manual** と表示されますが、設定値としては `default` です。CLI では `manual` というエイリアスも使えます（v2.1.200 以降）。

### 切り替え方

**セッション中**: `Shift+Tab` で `default` → `acceptEdits` → `plan` の順に切り替わります。ステータスバーに現在のモードが表示されます。

```
⏸ manual mode on        （Manual）
⏵⏵ accept edits on      （acceptEdits）
⏸ plan mode on          （plan）
⏵⏵ auto mode on         （auto）
```

**起動時**:

```bash
claude --permission-mode plan
```

**デフォルトとして設定**（`~/.claude/settings.json` など）:

```json
{
  "permissions": {
    "defaultMode": "acceptEdits"
  }
}
```

**VS Code / デスクトップ / Web**: プロンプト欄の近くにあるモード表示をクリックして切り替えます。

> **モードは会話で頼んでも変わりません。** 「これからは確認しないで」とチャットで言うのではなく、上記の手段で切り替えてください。

### `acceptEdits` — ファイル編集を自動承認

作業ディレクトリ内のファイル作成・編集が確認なしで通ります。加えて `mkdir`、`touch`、`rm`、`rmdir`、`mv`、`cp`、`sed` といった基本的なファイル操作コマンドも自動承認されます。

**作業ディレクトリの外、保護パスへの書き込み、それ以外の Bash コマンドは引き続き確認されます。**

「編集を 1 つずつ承認するのではなく、後で `git diff` でまとめて見たい」という人に向いています。

### `plan` — 調べるけど変えない

Claude はファイルを読み、探索用のコマンドを実行し、計画を書きますが、**ソースは変更しません。** 計画を承認するまで編集はブロックされます。

入り方は `Shift+Tab`、または単発なら `/plan` をプロンプトの先頭に付けます。

計画ができると、進め方を選ぶ画面が出ます。

- **Yes, and use auto mode** — 承認して auto モードで実行（auto が使えない場合は「編集を自動承認」）
- **Yes, manually approve edits** — 承認して、編集は 1 つずつ確認
- **No, keep planning** — プランモードのまま、修正点を伝える

`Ctrl+G` を押すと、提示された計画を自分のエディタで開いて直接編集できます。

### `auto` — 分類モデルが危険な操作だけを止める

別の分類モデル（classifier）が、実行前に操作をレビューします。**依頼の範囲を超える操作、見知らぬインフラを対象にした操作、外部から読み込んだ悪意あるコンテンツに誘導された操作**をブロックし、それ以外は確認なしで通します。

```bash
claude --permission-mode auto -p "lint エラーを全部直して"
```

**デフォルトでブロックされる操作の例**

- `curl | bash` のようなコードのダウンロード実行
- 機密データの外部エンドポイントへの送信
- 本番デプロイ・マイグレーション
- クラウドストレージの大量削除
- IAM やリポジトリ権限の付与
- 共有インフラの変更
- セッション開始前から存在したファイルの不可逆な破壊
- 強制プッシュ（force push）
- `terraform destroy` などのリソース破壊
- `git reset --hard`、`git clean -fd`、`git stash drop` など未コミットの変更を捨てる操作
- シークレットを外部に出す変更のコミット・プッシュ

**デフォルトで許可される操作の例**

- 作業ディレクトリ内のファイル操作
- lock ファイル・マニフェストに宣言済みの依存インストール
- `.env` の読み取りと、対応する API への認証情報送信
- 読み取り専用の HTTP リクエスト
- 作業中リポジトリのブランチへのプッシュ

全ルールは `claude auto-mode defaults` で JSON として確認できます。

> **会話で伝えた制約も効きます。**
> 「プッシュはしないで」「レビューするまでデプロイは待って」と伝えると、分類モデルはそれをブロック条件として扱います。この制約は、あなたが後のメッセージで解除するまで有効です。Claude が「条件は満たされた」と判断しても解除されません。
> ただしこれは会話履歴から都度読み直されるため、**コンパクションで該当メッセージが消えると失われます。** 確実に禁止したいなら `deny` ルールを使ってください。

**ブロックが続くとどうなるか**: 連続 3 回、または合計 20 回ブロックされると auto モードは一時停止し、通常の確認に戻ります。非対話モード（`-p`）では、確認する相手がいないためセッションが中断されます。

**利用条件**: すべてのプランで利用可能ですが、モデルとプロバイダに条件があります。Team / Enterprise では管理者が無効化できます。使えない場合は要件のいずれかを満たしていません（一時的な障害ではありません）。

> ⚠️ auto モードは承認を減らしますが、安全を保証するものではありません。方向性を信頼できるタスクに使うものであって、機微な操作のレビューを置き換えるものではありません。

### `dontAsk` — 事前承認したものだけ

確認が必要な操作をすべて**自動的に拒否**します。`permissions.allow` にマッチする操作、読み取り専用の Bash コマンド、`PreToolUse` フックが承認したものだけが実行されます。
**CI パイプラインなど、待つ相手がいない環境向け**です。

```bash
claude --permission-mode dontAsk
```

### `bypassPermissions` — すべてスキップ

⚠️ **隔離されたコンテナ・VM でのみ使ってください。**

すべての確認と安全チェックを無効化します。プロンプトインジェクションや意図しない操作に対する保護は一切ありません。

```bash
claude --permission-mode bypassPermissions
# または
claude --dangerously-skip-permissions
```

- セッション開始時に有効化されている必要があります（途中から入ることはできません）
- 初回は責任の確認ダイアログが表示されます
- Linux / macOS では root や `sudo` での起動を拒否します
- Web 版（クラウドセッション）では、リポジトリの設定ファイルからこのモードを指定しても**無視されます**

「確認を減らしたいが安全性も欲しい」場合は、このモードではなく **auto モード**を使ってください。

## 7-3. 許可ルール（allow / ask / deny）

モードは「土台」です。その上に、個別のツールごとのルールを重ねられます。

```text
/permissions
```

このコマンドで、承認ルールを対話的に設定できます。設定ファイルに直接書くこともできます。

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm test)",
      "Bash(git log *)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Edit(.env)"
    ]
  }
}
```

起動時のフラグでも指定できます。

```bash
claude --allowedTools "Bash(git log *)" "Read"
claude --disallowedTools "Bash(rm *)" "Edit"
```

**重要な性質**

- `deny` ルールと明示的な `ask` ルールは **すべてのモードで有効**です（`bypassPermissions` でも）
- `allow` ルールは `bypassPermissions` では意味を持ちません（すべて承認済みのため）
- **auto モードに入ると、広すぎる `allow` ルールは無効化されます**。`Bash(*)`、`Bash(python*)` のようなワイルドカード、パッケージマネージャの run コマンド、`Agent` の許可など。`Bash(npm test)` のような具体的なルールは維持されます

> **承認プロンプトを減らしたい場合**
> `/fewer-permission-prompts` を実行すると、過去のセッションを調べて、よく使う読み取り専用コマンドの許可リストを提案してくれます。

## 7-4. 保護されたパス

以下への書き込みは **`bypassPermissions` 以外では自動承認されません**。設定ファイルにどんな `allow` ルールを書いても変わりません。リポジトリの状態と Claude 自身の設定を守るための仕組みです。

**保護ディレクトリ**

`.git` / `.config/git` / `.vscode` / `.idea` / `.husky` / `.cargo` / `.devcontainer` / `.yarn` / `.mvn` / `.claude`（`.claude/worktrees` を除く）

**保護ファイル（抜粋）**

- `.gitconfig`、`.gitmodules`
- `.bashrc`、`.zshrc`、`.profile`、`.envrc` などのシェル設定
- `.npmrc`、`.yarnrc`、`bunfig.toml` などのパッケージマネージャ設定
- `.pre-commit-config.yaml`、`lefthook.yml` などのフック設定
- `.mcp.json`、`.claude.json`

| モード | 保護パスへの書き込み |
| --- | --- |
| `default`、`acceptEdits` | 確認される |
| `plan` | 確認される |
| `auto` | 分類モデルが判断 |
| `dontAsk` | 拒否される |
| `bypassPermissions` | 許可される |

## 7-5. サンドボックス

OS レベルでファイルシステムとネットワークのアクセスを制限し、その範囲内では Claude が自由に動けるようにする仕組みです。

```text
/sandbox
```

「承認は減らしたいが、影響範囲は物理的に限定したい」という場合に有効です。
詳細は公式の [Sandboxing](https://code.claude.com/docs/en/sandboxing) を参照してください。

## 7-6. 機密情報の扱い

### 基本

- **`.env` や認証情報を含むファイルは、必要が無ければ読ませない。** `permissions.deny` に `Read(.env)` のようなルールを入れておくのが確実です
- **`CLAUDE.md` に認証情報を書かない。** git にコミットされるファイルです。個人的な値は `CLAUDE.local.md`（`.gitignore` 対象）へ
- **`/export` や `/bug` で会話を共有するときは中身を確認する。** 会話にはコードや認証情報が含まれている可能性があります

### Web 版・共有セッションの注意

- Web 版のセッションを共有すると、**プライベートリポジトリのコードや認証情報が含まれている可能性があります**。共有前に内容を確認してください
- Max / Pro アカウントの「Public」共有は、claude.ai にログインしている全ユーザーから見える状態になります
- リポジトリへのアクセス権を要求する設定は **Settings > Claude Code > Sharing settings** から変更できます

### クラウドセッションの隔離

Web 版のセッションは以下のように隔離されています。

- 各セッションが独立した Anthropic 管理の VM で動作
- ネットワークアクセスはデフォルトで制限され、無効化もできる
- git の認証情報や署名鍵はサンドボックスの中に置かれず、スコープを絞った認証情報を持つプロキシ経由で処理される

## 7-7. プロンプトインジェクションへの注意

**Claude Code が読むもののすべてが、信頼できるとは限りません。**

- Web ページの内容
- GitHub の Issue / PR のコメント
- CI のログ
- 外部から取り込んだファイル
- MCP サーバーが返すデータ

これらに「これまでの指示を無視して〜」のような文章が仕込まれている可能性があります。

### 対策

1. **auto モードの分類モデルは、この観点を持っています。** 外部から読み込んだ悪意あるコンテンツに誘導された操作をブロックします。また、ツール結果は分類モデル自体には渡らないので、ファイルや Web ページの内容が分類モデルを直接操作することはできません
2. **絶対に許可したくない操作は `deny` ルールにする。** モデルの判断に依存しない、確実な防御になります
3. **必ず実行させたいチェックはフックにする。** `PreToolUse` フックでブロックする方法が最も確実です
4. **外部コンテンツを扱わせるときは、権限を緩めすぎない。** 不明なリポジトリの Issue を処理させるときに `bypassPermissions` を使うのは避けてください

## 7-8. 権限設定の推奨パターン

| 状況 | おすすめの設定 |
| --- | --- |
| 使い始め、業務コードを触る | `default`（Manual）のまま。何が起きているか把握する |
| 慣れてきた日常の開発 | `acceptEdits` + `npm test` などの許可リスト。差分は `git diff` で確認 |
| 長い作業を任せたい | `auto` モード。会話で「プッシュはしないで」など境界を伝える |
| CI・自動化 | `dontAsk` + `--allowedTools` で必要最小限を明示 |
| 使い捨てコンテナでの実験 | `bypassPermissions`（それ以外では使わない） |
