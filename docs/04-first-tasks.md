# 04. はじめての実践

> **この章でわかること**
> - コード理解 → 修正 → テスト → コミットまでの一連の流れ
> - よく使う作業パターン（リファクタ、テスト作成、レビュー、PR 作成）
> - 実際に打てるプロンプトの例

この章は**手を動かしながら読む章**です。適当なプロジェクトで `claude` を起動して、上から順に試してみてください。

---

## 4-1. ステップ 1: コードベースを理解する

新しいプロジェクトに入ったときや、久しぶりに触るコードを扱うときは、まず質問から始めます。

```text
このプロジェクトは何をするもの？
```

```text
どんな技術スタックを使ってる？
```

```text
エントリーポイントはどこ？フォルダ構成も説明して
```

```text
テストはどうやって実行する？CI では何が走ってる？
```

慣れてきたら、先輩エンジニアに聞くような質問もできます。

```text
ユーザー認証はどう実装されてる？セッション管理の仕組みも含めて教えて
```

```text
ExecutionFactory の API がこういう形になっている経緯を、git の履歴から調べて要約して
```

> **コツ**
> 「調べて」と頼むときは範囲を絞ってください。範囲を指定しないと大量のファイルを読み込んでコンテキストを圧迫します。
> 広く調べさせたいときは「**サブエージェントを使って調べて**」と付けると、別のコンテキストで調査して結果だけ返してくれます。

---

## 4-2. ステップ 2: 小さな変更をしてみる

まずは影響の小さいところから。

```text
README.md に「開発環境のセットアップ」セクションを追加して
```

Claude Code は次のように動きます。

1. 適切なファイルを見つける
2. 変更内容を提示する
3. （権限モードによっては）承認を求める
4. 編集を実行する

デフォルトの Manual モードでは 1 つ 1 つ承認を求められます。承認が煩わしくなってきたら `Shift+Tab` で `acceptEdits` に切り替えて、後から `git diff` でまとめて確認する進め方もできます。

## 4-3. ステップ 3: バグを直す

バグ修正は Claude Code が最も得意とする作業の 1 つです。

### エラーメッセージがある場合

エラーをそのまま貼り付けるのが一番速いです。

```text
テストを実行したらこのエラーが出た。原因を調べて直して。
エラーを握りつぶすのではなく根本原因に対処して。

TypeError: Cannot read property 'id' of undefined
    at getUserProfile (src/api/users.ts:42:18)
    at async handler (src/api/handler.ts:15:3)
```

### 症状だけがわかっている場合

「症状」「探すべき場所の当たり」「直った状態の定義」の 3 点を伝えます。

```text
セッションタイムアウト後にログインが失敗するという報告がある。
src/auth/ の認証フロー、特にトークンのリフレッシュ処理を確認して。
まず問題を再現する失敗テストを書いてから、それを通るように直して。
```

**「まず再現するテストを書いて」と頼むのは非常に有効です。** テストという客観的な合否判定ができると、Claude が自分で「直ったかどうか」を確認できるようになります。

---

## 4-4. ステップ 4: 検証させる

Claude Code に作業を任せるときの最重要ポイントは、**Claude 自身が結果を確認できる手段を渡すこと**です。

```text
実装できたらテストを実行して、失敗したら直して、通るまで繰り返して
```

```text
実装後に npm run build と npm run lint を実行して、
エラーが出たら直して。最後に実行結果を見せて
```

「できました」という報告だけでなく、**実行したコマンドとその出力を見せてもらう**ようにすると、自分で再実行しなくても確認できます。

## 4-5. ステップ 5: コミットして PR を作る

Git 操作も会話でできます。

```text
変更したファイルを教えて
```

```text
変更内容を分かりやすいメッセージでコミットして
```

```text
feature/user-validation という名前でブランチを切ってから、コミットして PR を作って
```


> コミットやプッシュは、こちらが明示的に頼まないと勝手に実行されません。逆に、任せたい場合ははっきりそう伝えてください。

## 4-6. よく使う作業パターン

### テストを書く

```text
src/utils/calculator.ts のユニットテストを書いて。
既存の src/utils/__tests__/ のテストのスタイルに合わせて。
書いたら実行して、通ることを確認して。
```

### リファクタリング

```text
認証モジュールをコールバックから async/await に書き換えて。
外部から見た振る舞いは変えないこと。
書き換えたらテストを実行して、既存のテストが全部通ることを確認して。
```

### コードレビュー

```text
/code-review
```

現在の差分をサブエージェントがレビューし、バグや改善点を報告します。
自分でレビュー観点を指定したい場合はこう頼みます。

```text
サブエージェントを使って、今の差分をレビューして。
エッジケース、競合状態、既存のミドルウェアとの一貫性を重点的に見て。
スタイルの好みではなく、正しさに影響する問題だけ報告して。
```

### セキュリティチェック

```text
/security-review
```

### ドキュメント更新

```text
今回追加した API エンドポイントの内容を docs/api.md に追記して。
既存の記述フォーマットに合わせて。
```

### UI の実装（画像を使う）

```text
[画像を貼り付け] このデザイン通りに実装して。
実装したらスクリーンショットを撮って元の画像と比較し、
違いを列挙してから修正して。
```

### 大きめの機能開発（インタビューさせる）

大きな機能は、いきなり実装させずに**まず Claude に質問させる**と精度が上がります。

```text
[作りたいものを一言で] を作りたい。
AskUserQuestion ツールを使って、詳しくインタビューして。

技術的な実装方針、UI/UX、エッジケース、懸念点、トレードオフについて聞いて。
当たり前のことは聞かず、私が見落としていそうな難しい部分を掘り下げて。
すべて洗い出せたら、完全な仕様を SPEC.md に書いて。
```

仕様ができたら **`/clear` して新しいセッションで実装させます。** 実装だけに集中したきれいなコンテキストで作業でき、参照できる仕様書も手元に残ります。

## 4-7. 段階的に進める

複雑なタスクは、手順に分けて指示すると成功率が上がります。

```text
以下の順番で進めて。各ステップが終わったら一度止めて報告して。

1. ユーザープロフィール用のデータベーステーブルを作る
2. プロフィールを取得・更新する API エンドポイントを作る
3. プロフィールを表示・編集できる画面を作る
```

---

## 4-8. うまくいかないときの立て直し方

| 状況 | 対処 |
| --- | --- |
| 明らかに違う方向に進んでいる | すぐ `Esc` で止めて、方向を修正する |
| 変更を取り消したい | 「さっきの変更を取り消して」と伝える、または `Esc` `Esc` で巻き戻す |
| 同じ指摘を2回してもまだ直らない | `/clear` して、学んだことを踏まえた**より具体的なプロンプト**で最初からやり直す |
| 話が脱線してコンテキストが散らかった | `/clear` |

**「2回直しても直らないなら、会話を続けるよりリセットしたほうが速い」** — これは覚えておく価値があります。失敗した試行がコンテキストに残り続けると、判断がさらに鈍るためです。
